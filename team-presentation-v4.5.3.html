Deployment Portal

A React webapp that turns HubSpot into a deployment-management tool for the CX team

What it is

  • React 18 web app at deployment-portal-instrumental.web.app
  • Consolidated PMO-style UI: projects, station kits, shipments, deployment milestones
  • Bidirectional with HubSpot — pulls on a schedule, writes back edits instantly

APIs it connects to

  • HubSpot Custom Objects (Projects, Shipments, Station Kits, Fleet Assets, CS Programs)
  • HubSpot v4 Associations (kit ↔ fleet asset labeled associations)
  • HubSpot Owners (DRI sync)
  • HubSpot Pipelines (stage Kanban)
  • Firebase Realtime Database + Firebase Auth (Google OAuth)
  • Anthropic Claude API (in-app Project Bot)
  • Slack incoming webhooks (feedback routing)

Why I built it — friction with HubSpot alone

  • Hard to share project documents with external stakeholders (CMs, SIs) without HubSpot licenses
  • Not AI-native — no inline Claude-assisted project status drafts or chat
  • Challenging UI — HubSpot is CRM-first; project tracking views clunky to assemble
  • No place for non-CRM data (checklists, training materials, internal hardware overrides)

Two workflows in one UI today

  • Instrumental Hardware Deployment — primary workflow (v4.x)
  • SI Partner Deployment — built by Sneha; uses the HubSpot "SI Partner Deployment" pipeline (SIRD → DFM → Quote → PO → Build → FAT → SAT → Live), si_admin role, All SI Projects view + Kanban

Splitting the Instrumental + SI workflows

  • Today both workflows live in the same app (toggled by role / sidebar tab)
  • Plan: separate UI experiences — same backend / same data store, distinct routes and navigation per workflow
  • Why: the workflows are different enough (different stages, different milestone definitions, different stakeholders) that one merged UI adds confusion. Separating lets each team optimize their view without stepping on the other.
  • Sneha owns the SI side; Asang owns the Instrumental side; backend stays shared

JWT — how auth flows

  1. User signs in with Google → Firebase Auth issues a JWT
  2. Every RTDB read/write + Cloud Function call carries the JWT in the Authorization header
  3. RTDB security rules (database.rules.json) check auth.uid + look up the user's role to allow/deny
  4. Cloud Functions check context.auth.uid then re-verify role from users/{uid}/role
  5. Tokens auto-refresh in the browser; no server-side session needed
Why this matters:

External users physically cannot read other projects' data — rules deny it at the database layer, not just in the UI. This was a finding addressed during the v3.0.0 security review.

What's under the hood

Frontend

  • React 18 + Vite
  • Single file src/App.jsx (~11,000 lines) — to be split as it grows
  • State: React useState + Firebase RTDB onValue listeners (no Redux / Zustand)
  • Bundle: ~770 KB main (gzip ~208 KB), code-split into react-vendor + firebase-vendor + xlsx-vendor chunks
  • UI: custom CSS-in-JS objects (no Tailwind), Instrumental color palette baked in
  • Multi-language UI (English, Español, Tiếng Việt, 繁體中文, 简体中文)

Data model

  • appState/projects/ — project list (synced from HubSpot)
  • appState/docData/{pid}/ — per-project state (projectDetails, hardware tracking, validation)
  • users/{uid} — user records + role
  • hubspotSync/log/ — every sync attempt
  • hubspotWriteback/log/ — every writeback attempt
  • auditLog/ — sensitive admin actions

Backend

functions/index.js · ~85 KB packaged · Node 20

  • 20+ callable functions spanning admin actions, HubSpot sync, writebacks, AI bot, Slack feedback
  • HubSpot sync: scheduled Tue/Fri 3 PM PT (scheduledHubspotSync) + on-demand (manualHubspotSync)
  • Writeback CFs:
    • writeProjectDateToHubspot
    • writeStageToHubspot
    • writeShipmentToHubspot
    • writeStationKitToHubspot
    • writeFleetAssetAssociation
  • Admin callables with audit logging on every sensitive op
  • provisionUser CF auto-creates @instrumental.com accounts on first sign-in

Database-level access control

Rules enforce role + per-project grants at the RTDB layer, not just in the UI. External users physically cannot read other projects.

Built with Claude Code — workflow, learnings, history

Common pitfalls — real lessons

  • Nested React components defined inside the parent cause rapid remount/unmount, swallowing local state → always define at module scope
  • Whole-node DB writes can wipe RTDB if local state is partial → field-level diffs only (v4.5.1 lesson)
  • "First non-X" heuristics break when HubSpot reorders schemas → use stable type IDs as consts (v4.5.2 lesson)
  • Server-side fetches need explicit error handling for HubSpot 429/5xx; otherwise sync silently produces partial data

Release workflow

  1. Bump package.json + README version row
  2. npm run build — verify clean
  3. firebase deploy --only [scoped]
  4. Test in production: Manual Sync + targeted UI checks
  5. Verify RTDB state via firebase database:get
  6. Git commit + co-author tag
  7. Zip into previous-versions/
  8. git push origin main
  9. Update auto-memory with learnings

Security

  • Passed security review v3.0.0 (April 2026) — 7 findings addressed in v4.0.0
  • DB-level access rules + audit log on all admin actions
  • HubSpot tokens as Cloud Functions env secrets — never in client
  • URL validation: https-only; javascript: / data: / file: blocked
  • Backups: RTDB daily snapshots, 7-day retention (enabled 2026-06-11)
